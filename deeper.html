Deeper · D0 · Operating rules

Ten cheap sites, one engine, and the rules that keep it honest

The earlier documents describe an architecture. This one commits to it: the named third parties and what they cost, the machine it runs on, the bus and the harness as contracts rather than boxes, and the decision rules written as numbers a reviewer can argue with. The test is not whether the diagram is elegant. It is whether a person who disagrees with a decision can find the rule that caused it.

What this layer adds
  • The product is the differentiator, not the site. Ten storefronts from one template, identical code, different content. The engineering budget goes into deciding what to stock, what to spend, and what to kill.
  • One small machine, Postgres as the bus. At ten products the queue is a Postgres table with FOR UPDATE SKIP LOCKED, not a message broker. The interface is written so the broker can arrive later without touching agent code.
  • Same agent, different config. A reorder agent for perishable groceries and one for sunglasses are the same code and the same loop. Shelf life, review period and service level are configuration, and this page shows the file.
  • Agents never call agents. They publish facts and propose actions. Everything that writes goes through one gateway with one policy file. This is what keeps five or six people in control of ten autonomous storefronts.
This is implemented, not just described

The engine in engine/ runs these rules on 90 days of seeded history with no dependencies. cd engine && python3 run.py ui opens an operator console at 127.0.0.1:8787 where a cycle can be run and watched job by job, proposals approved or rejected, and every number clicked back to the query that produced it. python3 run.py demo prints the same decisions in a terminal, and this static snapshot is what run.py console generates — the same decisions, read back out of the database, with every intermediate number, the gateway's verdict on each proposal and the full audit trail.

Portfolio economics: why the site must be cheap

The strategy is a portfolio bet. Ten products launch, two win, two are ambiguous, six die. The value of the system is not in making any one storefront beautiful. It is in shortening the time to a correct verdict and in spending nothing on the six that die.

LeverBad versionWhat this architecture doesWhy it pays
Cost of a launchBespoke site per product, two weeks of designOne template, content-only launch, under a dayTen launches cost one launch
Cost of a wrong keepThree months of ad spend plus a reorder on a dead SKUFixed experiment budget per product, hard kill thresholdsThis is the single largest avoidable loss in the model
Cost of a wrong killA good product killed because the checkout was brokenThe verdict agent separates product failure from site failure before it recommends a killProtects the two winners that pay for everything
Cost of being slowMonthly reviews by people reading spreadsheetsDaily guardrails, weekly reallocation, verdicts on a fixed clockCompounding: the winner gets budget six weeks earlier
The one metric the whole system optimises

Not revenue, not ROAS. Contribution margin per order after advertising, returns and payment fees — and for the portfolio, contribution margin per euro of working capital per week. Every rule below resolves to one of those two. When two agents disagree, the arbitration is settled by whichever action improves the second number, because working capital is the binding constraint, not attention.

What is deliberately not here yet

No Temporal Cloud, no Service Bus, no Fivetran, no Triple Whale, no Kubernetes, no data warehouse. Each of those is the right answer later, and the scale plan says at which phase and on what trigger. Buying them at ten products would add about €1,500 a month and a second person's worth of operational surface for capability nobody is using yet. The architecture earns the right to them by hitting a stated threshold: Postgres queue depth sustained over 5,000 jobs, or a saga that needs a timer longer than 24 hours, or a third engineer joining.

The bus, concretely

A bus here means one thing: work is handed over as a durable row, not as a function call. If the process dies mid-decision, the work is still there, exactly once, and the next worker picks it up. That property is what lets ten storefronts run unattended overnight.

Figure D0.1: Phase-1 bus. The outbox pattern means an event is never published unless the database write committed, and never lost if it did.

The five rules that make a Postgres queue safe

RuleMechanismWhat it prevents
Exactly-once effectEvery action carries an idempotency_key = hash(agent, intent, business keys, period). The gateway stores it unique; a replay returns the first resultTwo purchase orders for the same need, two budget changes from one retry
Ordering where it matterssession_key on the job row (usually sku or campaign_id); a worker holds an advisory lock on that key for the runTwo workers reordering the same SKU concurrently
No lost eventsTransactional outbox: the fact and its event commit together, a relay moves them to the queue"We wrote the order but never re-forecast"
Bounded retries5 attempts, exponential backoff with jitter, then dead letter with the full traceA poison message burning tokens all night
Fair schedulingPer-topic concurrency caps and a per-agent token budget checked before the model callA marketing backfill starving the order pipeline, and a runaway bill

The swap path is explicit. Agent code only ever sees bus.publish(topic, key, payload) and bus.subscribe(topic, handler). Phase 2 replaces the driver with Azure Service Bus sessions; anything with a timer longer than a day, or a multi-step commit that must unwind, moves to a Temporal workflow. Nothing in the agents changes.

The harness contract: one file per agent

The harness is everything around the model that makes it useful and safe: what it is allowed to read, what it may propose, how many steps it gets, what counts as evidence, what happens when it is wrong. The seven stages describe the loop. What follows is the artefact that configures it — and the direct answer to "is it really the same agent for groceries and sunglasses?"

agent: reorder
version: 7
model:
  plan:   claude-sonnet-5-5      # chooses among options, writes rationale
  extract: claude-haiku-5-5      # supplier emails, confirmations
  max_steps: 12
  token_budget_month: 1_200_000  # enforced by the gateway, not by trust

reads:                            # MCP read tools; each returns evidence ids
  - sales_panel(sku, from, to)           # units, price, discount, availability%
  - availability_history(sku, from, to)
  - lost_demand_signals(sku, from, to)   # OOS sessions, back-in-stock, searches
  - returns_by_variant(sku, window)
  - supplier_terms(supplier_id)          # MOQ, case pack, lead-time distribution
  - open_orders(sku)
  - cash_position()

writes:                           # the ONLY side effects; typed, tiered
  - propose_reorder{sku, qty, need_by, supplier_id, rationale, evidence[]}
  - propose_markdown{sku, pct, floor_reason}
  - raise_anomaly{kind, severity, note}

engines:                          # deterministic; the model may not do this arithmetic
  demand: censored_poisson_v3     # reconstructs demand from availability
  quantity: newsvendor_quantile   # service level -> order-up-to -> MOQ rounding

policy:                           # <-- the entire difference between businesses
  review_period_days: 7
  shelf_life_days: null           # 3 for fresh bread, 14 for dairy, null = durable
  service_level_by_class: {A: 0.97, B: 0.93, C: 0.85}
  cover_cap_weeks: 16             # overbuy guard
  min_history_days: 28            # below this: propose a test buy, never a bulk buy
  markdown_curve: none            # linear_from_day_60 for perishables
  trigger: [schedule, stockout_risk_below_days(10), verdict_published]
  autonomy:
    auto_execute_below_eur: 2_000
    maker_checker_below_eur: 10_000
    human_signal_above_eur: 10_000
    daily_cap_eur: 15_000

verify:                           # stage 5; failing any one blocks the write
  - qty_within(0.4, 2.5, of: last_12w_sales)   # sanity band
  - cover_after_order_lte: 16w
  - every_number_cited_has_evidence_id
  - cash_after_order_gte: 12w_runway

A supermarket replenishing yoghurt sets shelf_life_days: 14, markdown_curve: linear_from_day_7, review_period_days: 1. A sunglasses brand sets shelf_life_days: null and a weekly review. Same loop, same engines, same gateway, same audit trail. What is not configurable is the part that makes it trustworthy: evidence ids on every number, the deterministic quantity engine, and the tier ladder.

Why the model is kept away from the arithmetic
Decision
Language models choose between options and explain them. A deterministic engine computes how much.
Reason
A reorder quantity must be reproducible, testable against history, and defensible to a supplier. A sampled token stream is none of those.
Consequence
Forecast quality becomes a measurable engineering problem (backtest error) rather than a prompt-tuning exercise, and the same engine is reused by the pricing and verdict agents.

Interaction rules R1–R12

These are the rules that stop twelve autonomous processes becoming an argument. They are enforced in code, not in prompts.

#RuleEnforced by
R1No agent calls another agent. They publish facts and subscribe to topics.No agent-to-agent HTTP route exists; the harness has no such tool
R2Exactly one agent owns each write. Pricing owns price, reorder owns quantity, marketing owns budget.Gateway policy maps intent → allowed agent; anything else is rejected and logged
R3Every number in a rationale carries an evidence id pointing at a stored query result.Verification stage rejects uncited numerals
R4Actions are tiered by money and reversibility, not by confidence.Tier ladder in the gateway; the agent cannot choose its own tier
R5Spend and stock cover are coupled. No acquisition budget on a SKU with under two weeks of cover.Deterministic coupling table (see flows), evaluated before every budget write
R6Changes have a cooldown. A lever moved today is frozen for its cooldown window.last_changed_at per lever, checked in the gateway
R7A decision with less than the configured minimum exposure is "not yet known", never "bad".Minimum-exposure gate in every verdict and pause rule
R8Promotions, campaigns and price changes are published as plans before they run, and become forecast features.Forecast feature store reads the plan table; holdouts preserved
R9Anything irreversible outside the company — money leaving, supplier bank details, a domain released, a customer email blast — is never fully autonomous.Hard-coded T3 list, independent of tiers
R10Each agent has a monthly token and action budget. Exhaustion degrades to rules-only mode, it does not stop the business.Gateway counters; fallback policies per agent
R11Every autonomous decision is reversible within one command for 7 days (reverse entry, not deletion).Append-only ledger + compensation handlers per intent
R12If two agents' proposals conflict, the one improving contribution margin per euro of working capital wins; ties go to the human queue.Arbitration function in the control tower, logged with both proposals

The honest answer on open source

The concern raised in the brief was not ideological, it was about delivery risk: open source can mean more people, more integration work, and bugs owned by nobody. The rule that resolves it:

CategoryPositionExamples here
Libraries inside our processUse freely. No operational surface, replaceable in an afternoonPostgres drivers, Zod/Pydantic schemas, LightGBM, statsforecast, OPA as a library, OpenTelemetry SDKs
Infrastructure we would have to operateAvoid at this size. An on-call rota of five people cannot also run a broker and a warehouseSelf-hosted Kafka, self-hosted Temporal, self-managed Postgres, Airflow
Agent frameworksBorrow the ideas, keep the harness thin and ours. The valuable part is validation, tiering and evidence, which no framework will enforce the way the business needsLangGraph and Agent Framework patterns are referenced; neither is a dependency on the critical path
Anything touching money, tax or customer payment dataBuy. Liability transfer is the pointShopify Payments, Stripe, Xero

Said plainly

Everything in phase 1 can be built by one engineer, and I would rather state the ceiling than discover it: the moment two storefronts are winners with real volume, there must be a second engineer whose job is to keep it running while the first keeps building. Scaling without that is how a working system becomes an outage with no owner.

Build order: what exists when

Days 1–5

The spine

Postgres schema (ledger, outbox, queue, snapshots), Shopify adapter with idempotent webhooks, the hourly inventory snapshot job, the action gateway with the policy file and tier ladder, OpenTelemetry traces. Nothing intelligent yet, and it is the part everything else depends on. The snapshot job is first because missing availability history is unrecoverable — the towel case on the next page is exactly that failure.

Days 6–10

Agent one: marketing allocation

Ad pollers, server-side conversions, the margin-based metric definitions, pacing guards hourly, the daily pause/scale rules, the weekly channel bandit. First week runs in shadow mode: it proposes, a human approves, and we compare.

Days 11–16

Agent two: reorder

Censored-demand engine with backtests against the existing sales history, the newsvendor quantity engine, supplier terms, purchase-order proposals under maker-checker. Backtest first: if it cannot beat the current reorder decisions on last year's data, it does not go live.

Days 17–21

Agent three: product verdict

Funnel decomposition, the product-versus-site discriminator, the fixed experiment budget, verdict publication and the kill runbook. This is the one that turns ten launches into a portfolio instead of ten hopes.

Week 4 onward

Earn each upgrade

Autonomy rises only where the evaluation set says it should: an agent moves from shadow to auto-execute when it matches or beats human decisions on a 30-decision backtest and has a clean week of guard trips. Every threshold in the config files is version-controlled, so a change of behaviour is a reviewable diff.
