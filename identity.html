Deep dive C · Identity, secrets and runtime

Every agent is a principal. No agent holds a secret.

In an autonomous company, the "employees" are software. They need the same things human staff need: an identity, least-privilege access, credentials that expire, and an audit trail of who did what. This page covers agent identity, token exchange (including on-behalf-of), runtime secret resolution, and how the harness reaches Azure AI Foundry without API keys.

Azure architecture

Azure architecture. Numbers follow one request: an owner signing in, and an agent calling a Foundry model.

#Step
1An owner signs in with Entra ID, with MFA and Conditional Access.
2The owner console receives the owner's token.
3For an approval, the console exchanges that token on behalf of the owner (OBO), so the audit log names the person, not the app.
4An agent's decision goes from the harness to the Action Gateway as a proposal. Every service gets its tokens from its own managed identity, so there are no passwords in code.
5The harness calls a model through API Management, which checks quotas and content safety.
6API Management calls the Foundry agent and model with its own identity. No API keys anywhere.
7The gateway writes to PostgreSQL using a short-lived Entra token as its password.
8Adapters fetch only their own vendor secret from Key Vault, at the moment they need it.

Runtime secret and token flow

Configuration is resolved at runtime, not baked into builds. Global bootstrap settings come from the environment. Everything sensitive is fetched by identity from the secret store, validated against a strict schema, and cached briefly.

On-behalf-of (OBO) and delegated access

Where OBO is used

  • Human exception approvals (T3). An owner signs in to the console. The console backend exchanges the owner's token for a downstream token (OAuth 2.0 on-behalf-of). The Action Gateway and Ledger then see the owner's identity, so the audit trail says "approved by owner X", not "approved by the console service".
  • Database access as the caller. Postgres uses Entra authentication, with a short-lived access token as the password. Row-level security policies key off that identity, so a console user sees only what their role allows.

Where it is not

  • Autonomous agents act as themselves, with their own workload identity. They are not on behalf of any person. Pretending an autonomous action was taken by a human would corrupt the audit trail.
  • When one agent delegates to a sub-agent, the sub-agent gets a narrowed token via token exchange: same case, fewer scopes, shorter lifetime. It never inherits the parent's full rights.

Operational rules that make this production-safe

RuleWhy
Strict config schemas, fail closed. Secret bundles are validated at load, and unknown keys are rejected so typos are caught. Conditional rules apply, e.g. if any adapter credential is present, all the required ones must be.A half-configured adapter that "sort of works" is worse than one that refuses to start.
Short-TTL caches with in-flight deduplication. Tokens and secrets are cached (minutes), refreshed before expiry, and concurrent requests share one fetch.Stops token storms at scale; removes secret-store latency from the hot path.
Expired-token handling breaks loops. Specific expiry errors clear the cache and force a fresh acquisition. Repeated failure opens a circuit, not an infinite retry.A classic production failure is a redirect or retry loop on an expired assertion.
Separate identities per environment. Preview and staging environments get their own identities, database and model deployments.A staging agent can never touch production suppliers.
Long jobs refresh credentials mid-flight. Batch jobs such as backfills and training re-acquire tokens between stages.A multi-hour job must not fail at minute 61 because a token expired.
No tokens in logs. Log which identity called what, with latency, never the token itself.Traces are widely readable; tokens are bearer credentials.
Private networking. Private endpoints for Key Vault, Postgres, Service Bus and Foundry. Egress allow-list per adapter.Stolen credentials are useless from outside the network boundary.

  ledger-database/

Restricted keys are used wherever vendors support them. For example, the Stripe key used by the refund adapter can create refunds and read charges, but cannot create payouts.
