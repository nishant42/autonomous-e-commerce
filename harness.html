Deep dive A · Agent harness

The harness is what makes a stateless model safe to run a company

A model is a stateless function from text to text. It has no memory, no permissions, no notion of truth and no stopping condition. Everything that makes it an agent is the harness: the deterministic runtime that decides what the model sees, what it may touch, when it must stop, whether its output is valid, and what is remembered.

The one rule
  • The harness enforces integrity. The prompt shapes intent. The harness does format validation, closed enums, existence and ownership checks, limits and persistence, and returns structured errors so the model can self-correct. The prompt and tool descriptions guide judgement: which option, what tone, when to ask.
  • If the harness is making a judgement about meaning, it is in the wrong place. If the prompt is responsible for an invariant, it is in the wrong place.

Harness architecture

Agent harness: the code wrapped around every agent. The model only decides; everything in the box checks, limits and records it.

The seven stages

Figure A.1: Harness stages. Stages ③ and ④ loop. Guardrails apply at every stage.

① Intake

What happens

  • A workflow activity or event handler creates a task envelope: agent ID and pinned version, task type, business key, correlation ID, idempotency key, deadline, token and tool-round budget.
  • The kill-switch and quarantine registry is checked first. A halted agent never starts.
  • Deduplication: if the idempotency key already completed, the stored result is returned.

Why it matters

Pinning prompt, tools and model version together makes every decision reproducible. Budgets set here are enforced mechanically later, so cost and latency are bounded before the first token.

② Context engineering

The single biggest lever on quality. A resolver builds what the model sees on this turn, from typed inputs only. It never scrapes free-form blobs or guesses.

③ Agentic loop

// Simplified harness loop (TypeScript-flavoured pseudocode)
async function runAgent(task: TaskEnvelope): Promise<AgentResult> {
  assertNotHalted(task.agent);                              // kill switch / quarantine
  const ctx = await resolveContext(task);                   // stage ②: typed, fails loudly
  const abort = AbortSignal.timeout(task.deadlineMs ?? 180_000);  // one shared deadline
  let res = await model.respond({ instructions: agent.prompt, input: ctx, tools: agent.tools }, { signal: abort });

  for (let round = 0; round < agent.maxToolRounds /* 8 */; round++) {
    const calls = res.toolCalls();
    if (calls.length === 0) break;
    const outputs = await Promise.all(calls.map(c => toolGateway.execute(task, c)));  // stage ④
    budget.charge(res.usage);                                // token budget enforced per round
    res = await model.respond({ previous: res.id, toolOutputs: outputs }, { signal: abort });
  }

  if (res.hitRoundCeiling) return escalate(task, "tool-round ceiling", res);   // honest, not silent
  const output = parseStrict(agent.outputSchema, res.text);                    // typed or fail
  const verdict = await verify(task, output);                                  // stage ⑤
  if (!verdict.pass) return retryOrEscalate(task, verdict);
  return commit(task, output);                                                 // stage ⑥
}

Bounded

Maximum tool rounds (8), one shared wall-clock deadline (so per-round timeouts cannot add up past it), and token budgets per task and per agent per day.

Parallel where safe

Independent read tools run concurrently. Writes are never tools; they are proposals, handled in stage ⑥.

Honest ceilings

If the loop hits its limit, the result is marked incomplete and escalated. The harness never makes up a confident answer.

Anti-patterns the harness forbids
  • Silently inferring a missing argument (e.g. defaulting page or supplier). This hides a contract violation, so the model never learns it made a mistake.
  • Silently downgrading a plan when IDs do not resolve, e.g. showing "all items" when the model named one unknown item. If the IDs are wrong, return an error. Being "forgiving" here is actively wrong.
  • Synthesising user-facing text on the model's behalf ("Done!") when the model produced none. Fail honestly and fix the prompt.
  • Returning ok: true and then discarding the model's output later. The model cannot learn from feedback it never receives.

⑤ Verification

Deterministic checks run first because they are cheap and exact: arithmetic, sums, ranges, referential integrity, policy pre-check. An independent checker runs second for anything customer-facing, money-moving or T2. The checker uses a different prompt, ideally a different model family, and read-only tools. The maker never marks its own work.

⑥ Commit and memory

  • Side effects leave only as Action Proposals to the Action Gateway. The harness itself holds no vendor credentials.
  • The harness persists the turn: messages, tool-call log (resultId, args, preview, audit metadata such as caller identity and scope), verifier verdict, cost.
  • Memory hygiene: the summariser skips refusals, failures and unverified claims; stacked refusals are filtered from the replay tail; infrastructure errors (e.g. a content-safety block) use a message that is distinct from a model refusal, so they are never learned as behaviour.

⑦ Observe and evaluate

Every stage emits OpenTelemetry spans: task → model call → tool call → proposal → execution, with token counts, cost, latency, validation errors and verifier verdicts. The Sentinel watches these as behaviour metrics, and a daily sample goes to the Auditor and into the evaluation datasets. See Evaluation & observability.

Model decides vs harness decides

The model decides

  • Whether to answer directly, call tools or ask a clarifying question
  • Which tools, in what order
  • How to trade off options, e.g. expedite vs split vs wait
  • What to say, and in what tone
  • Which Action Proposal to make, with what parameters

The harness decides

  • What context exists this turn
  • Which tools exist at all for this agent
  • Whether arguments are valid, exist and are owned
  • When the loop stops (rounds, time, tokens)
  • Whether output passes verification
  • What is remembered and what is forgotten
  • Whether a proposal executes (via the gateway)
