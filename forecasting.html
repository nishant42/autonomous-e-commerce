Deep dive I · Forecasting and ML models

How demand is forecast, and every other model the company runs

Forecasting is the engine of the supply side: every reorder, price move and campaign starts from it. This page covers the problem framing, the model portfolio, the features, how forecasts become purchase decisions, the short-term demand-sensing path, the other ML models (classification, regression, bandits), and the MLOps that keeps them honest.

The design in five points
  • Probabilistic, not point forecasts. Every SKU × node gets P10 / P50 / P90 daily demand for 26 weeks. Purchasing decisions need the spread, not just the average.
  • A portfolio, chosen per segment. A global LightGBM quantile model covers regular sellers, Croston/TSB covers the intermittent long tail, similarity-based curves cover new products, and seasonal-naive/ETS baselines always run as a safety net.
  • Hierarchically coherent. Forecasts are reconciled (MinT) so variants add up to products, collections, categories and the total. Finance and procurement then see the same numbers.
  • Stock-outs are not low demand. Sales during stock-outs are treated as censored, so the model doesn't learn that "we sold nothing" means "nobody wanted it".
  • LLMs never produce the numbers. They extract product attributes for cold start and explain anomalies. Forecasts come from ML, and decisions from optimisation plus policy.

What makes premium linen hard

Intermittent long tail

Most size × colour variants sell a few units a week, with many zero days. Classical models over-forecast these, and pure ML models are noisy.

Censored demand

During a stock-out, sales are zero but demand isn't. Without correction the model learns to under-forecast exactly the items that sell out.

New collections

Seasonal launches have no history. Their first 8 weeks are the most expensive to get wrong, because the whole pre-season buy depends on them.

Our own actions move demand

Promotions, price changes and campaigns cause demand. They must be features the forecast knows about, or the forecast chases its own tail.

Model portfolio

SKUs are segmented each night using the classic demand classification: ADI (average inter-demand interval) and CV² (squared coefficient of variation of non-zero demand), plus product age. Each segment gets the model family that fits it; the backtest picks the winner per segment.

Why not a deep-learning forecaster or an LLM "time-series foundation model"?

At about 3,000 short, sparse series, gradient boosting plus statistical models is more accurate, cheaper, faster to retrain and easier to explain. A pretrained time-series foundation model is worth a challenger slot in the backtest; it gets promoted only if it wins on held-out data. Generative LLMs are never used to produce demand numbers.

Censored-demand correction

# For each SKU × node × day
in_stock_share  = in_stock_hours / trading_hours          # from Ledger availability events
observed_sales  = units_sold
if in_stock_share >= 0.9:
    demand = observed_sales                               # clean day
elif in_stock_share > 0:
    demand = observed_sales / in_stock_share              # scale up partial-availability days (capped)
else:
    demand = NaN                                          # fully stocked-out: masked from the loss,
                                                          # not treated as zero demand
# Training uses a masked loss so censored days never teach the model "nobody wanted it".

From forecast to purchase decision

The forecast is not the decision. The Replenishment Planner turns the forecast distribution and the supplier lead-time distribution into an order quantity, and policy then constrains it.

Continuous replenishment (core range)

An (R, S) periodic-review, order-up-to policy, solved by Monte Carlo simulation:

  • Draw 5,000 samples of demand over (lead time + review period), using demand samples from the forecast and lead times from the supplier scorecard distribution.
  • Order-up-to level S = the service-level quantile (97% for A-class, 93% B, 85% C).
  • Order quantity = S − (on hand + on order − backorders), rounded up to the case pack and MOQ.
  • Then caps: at most 16 weeks of cover, and open-to-buy and cash-runway rules.

Seasonal one-shot buys (new collections)

A newsvendor decision, because unsold seasonal stock is marked down:

Cu = price − cost          # margin lost per unit short
Co = cost − salvage        # loss per unit left over
critical_ratio = Cu / (Cu + Co)
Q* = F⁻¹(critical_ratio)   # quantile of season demand

e.g. duvet cover: price €249, cost €92,
     end-of-season outlet value €60
Cu = 157, Co = 32 → critical_ratio = 0.83
→ buy the P83 of season demand, split into
  an initial buy + an option re-order

MLOps: keeping models honest

Nightly pipeline

Azure ML pipeline at 02:00: build features → segment → train portfolio → backtest → register → infer → reconcile → publish fcst-vN to the Ledger by 04:00. Retrains take minutes on CPU.

Promotion gate

Rolling-origin backtest over the last 12 weeks. A new model is published only if WAPE is no worse than champion + 3%, bias is within ±5% and P10-P90 coverage is 75-85%. Otherwise the last good forecast stays live.

Drift monitoring

Feature drift (PSI), live error vs backtest error, and bias by segment. Alerts go to the Sentinel. Sustained bias triggers retraining or rollback, not a human.

Champion / challenger

Challengers (a foundation model, a new feature set) run in shadow every night and are compared on the same backtest. They are promoted only on evidence.

Reproducibility

Every forecast stores model version, feature snapshot and data watermark. Any purchase order can be traced to the exact forecast that justified it.

Explainability

SHAP values per forecast feed the Planner Explainer, which writes, for example: "+38% vs last month: January white sale flag, email campaign, price −10%."
