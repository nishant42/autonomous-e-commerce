02 · Agent hierarchy

Agents, sub-agents, and exactly what each may touch

Four levels. The owners set policy. The Control Tower supervises. Department supervisors route work. Specialist agents do narrow jobs, often with sub-agents such as extractors and verifiers. Every agent has a mandate, a tool allow-list, an action list with risk tiers, and a declared technique.

Hierarchy

Figure 2.1: Agent hierarchy: L0 owners → L1 Control Tower → L2 department supervisors → L3 specialists and sub-agents (full detail in the tables below). Supervisors route work and start workflows. They do not hold business logic.

Why supervisors are thin

A supervisor that "thinks" about the business becomes a single point of cognitive failure and is hard to evaluate. Here, supervisors map events to workflows and agents; that is mostly deterministic code with an LLM classifier for ambiguous inbound items such as an unlabelled supplier email. The domain knowledge lives in specialists that can be tested narrowly.

Legend

LLM language, ambiguity, unstructured input · ML statistical prediction · Rules policy / thresholds · Workflow durable multi-step process · Deterministic plain code. Action tiers: T0 auto · T1 auto + sampled audit · T2 verifier / panel required · T3 human exception.

Every agent ships with a contract

An agent is a registered, versioned artefact, not a prompt in a string. The registry drives the tool allow-list, identity, limits and evaluation gates.

agent: procurement-agent
version: 3.4.1                    # prompt + tools + model pinned together
owner_domain: procurement
identity: mi-agent-procurement   # its own workload identity (never shared)
model_policy:
  default: frontier-reasoning      # routed via AI gateway
  fallback: frontier-alt
  max_tool_rounds: 8
  timeout_s: 180
  token_budget_per_task: 60000
tools:                            # allow-list; everything else is invisible
  - get_reorder_recommendations
  - get_supplier_terms
  - get_budget_position
  - build_po_draft                # deterministic PO Builder
  - propose_action                # only way to cause a side effect
actions:
  CreatePurchaseOrder: { tiers: { T0: "<=5000", T1: "<=20000", T2: "<=60000", T3: ">60000" } }
  AmendPO:            { tiers: { T1: "qty_delta<=20%", T2: "otherwise" } }
evaluation:
  offline_suite: procurement-golden-v12   # must pass >= 97% before promote
  shadow_days: 7
kill_switch: procurement.*
