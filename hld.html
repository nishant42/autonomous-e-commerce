Six planes, one choke point for side effects

The platform separates thinking (the agent runtime) from doing (the Action Gateway and adapters) and from remembering (the data plane). Events connect them and durable workflows sequence them. Security and observability span all of them.

Plane responsibilities

PlaneResponsibilityKey design choices
① IntegrationTranslate the outside world into typed events and commandsVerify webhook HMAC signatures. Inbox deduplication by provider event ID. One adapter per external system behind a stable internal contract (anti-corruption layer).
② Event backboneAsynchronous, durable fan-out between domainsService Bus for business events (sessions give per-SKU/per-PO ordering, DLQ, scheduled delivery). Event Hubs for high-volume telemetry. CloudEvents envelope with schema registry.
③ OrchestrationMulti-step, long-running, must-complete processesTemporal durable workflows. Timers of days or weeks (PO acknowledgement SLA), retries with backoff, sagas with compensation, full history replay.
④ Agent runtimeRun LLM, ML and rules agents safelyStateless harness pods. Model access only through the AI gateway (routing, quotas, caching, content safety). ML models served as versioned endpoints.
⑤ Action planeThe only path to side effectsPolicy-as-code (OPA/Rego). Spend and velocity counters in Redis. Idempotency table in Postgres. Tiered approval (verifier, panel, human). Immutable audit.
⑥ DataShared truth, memory and analyticsPostgres is the operational truth with an append-only ledger. The lakehouse holds history, features and training data. AI Search covers policy and contract retrieval.
Control planeGovern the fleetAgent registry (versioned contracts), kill switches, quarantine, evaluation gates, and a console for owners.

Deployment topology

Regions

Primary: UK South. Warm DR: West Europe, with Postgres geo-replica, Service Bus geo-DR alias and Temporal multi-region namespace. RPO ≤ 5 minutes, RTO ≤ 1 hour.

Environments

dev → staging (uses sandbox Shopify, Stripe test mode and supplier simulators) → prod. Each environment has separate identities, secrets and model deployments. Agents are promoted only after they pass evaluation gates.

Network

Private endpoints for Postgres, Service Bus, Key Vault and Foundry. Egress goes through Azure Firewall with an allow-list per adapter. Browser-automation workers run in an isolated subnet with no path to internal data.

Decision

Why a single Action Gateway instead of giving each agent its own API clients?

Chosen
Every side effect goes through one gateway, which enforces policy, limits, idempotency, tiering and audit in one place.
Rejected
Agents holding vendor SDKs and credentials (for example an agent calling Stripe directly).
Why
Safety controls are only as strong as their weakest bypass. One choke point makes limits provable. A kill switch becomes a single flag. Credentials never reach model context. Audit is complete by construction.
Cost
The gateway is a critical dependency, so it is kept stateless, horizontally scaled and deployed in two regions. Every new action type needs a schema and a policy, which is the point.
