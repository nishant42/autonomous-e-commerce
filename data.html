04 · Shared-state / data architecture

One truth per fact, events for everyone else

Agents are stateless. That is a feature, as long as the company's state is kept outside them, reliably. This page covers who is the source of truth for each fact, how writes become events, how agents read a consistent picture, and how agent memory is kept from poisoning itself.

Write path: transactional outbox

A state change and the event announcing it are committed in the same database transaction. A relay then publishes the outbox rows to Service Bus. This removes the classic dual-write bug, where the DB committed but the event was lost, or the reverse.

Figure 4.1: Outbox pattern. Optimistic concurrency (the version column) stops two writers from overwriting each other, and sessions keep per-aggregate ordering.

Consistency model

Strong inside an aggregate

A PO, a SKU's price or a refund is changed only by its owning service, in one transaction, with optimistic locking. Money and stock are never eventually consistent with themselves.

Eventual across domains

Marketing learns about low stock within seconds, not in the same transaction. Every consumer is idempotent (it deduplicates by event ID) and tolerates reordering by checking aggregate version.

Reconciled against the outside

Hourly, the 3PL stock snapshot and Stripe balance are compared with the Ledger. Drift beyond tolerance raises recon.break. Corrections are posted as compensating movements; history is never edited.

How an agent reads "the state of the company"

Agents do not query raw tables. They receive a typed context snapshot built by a resolver for their task, and they can pull more through read tools. Each snapshot carries an as_of watermark (the event offset), so a decision can later be replayed with exactly what the agent knew.

Why a typed snapshot and not "let the agent query SQL"?

Free-form queries make agents slow, expensive and non-reproducible, and they widen the attack surface. A typed snapshot is the contract between the platform and the agent. If a required field is missing, the harness fails the task loudly. It does not let the model guess.

Event contracts

All events use a CloudEvents envelope, with JSON Schemas in a registry. Schema changes are backward compatible: add optional fields only. A breaking change means a new event type version (po.created.v2) with both versions published during migration.

Refusals, failed attempts and unverified claims are never written into the summary, so one bad turn cannot teach the agent to repeat it.

Memory poisoning is a real production failure mode

If an agent refuses once and a naive summariser writes "assistant refused" into its memory, the agent can keep refusing on every later turn. So refusals and failures are never written into long-term memory, and infrastructure errors use a message that cannot be mistaken for a model refusal. This applies to every supplier and customer thread.
